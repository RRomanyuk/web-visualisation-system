# Веборієнтована система візуалізації даних з відкритих джерел

Дослідницький прототип. Вимоги — [docs/requirements.md](docs/requirements.md).

## Структура

```
backend/    FastAPI + SQLAlchemy + pandas — API та модуль обробки даних
frontend/   React + Vite (+ Plotly.js далі) — інтерфейс і візуалізація
docs/       вимоги
```

## Запуск

### Бекенд

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # Linux/macOS
pip install -r requirements.txt
copy .env.example .env         # Windows  (cp .env.example .env — Linux/macOS)
uvicorn app.main:app --reload
```

Бекенд: http://localhost:8000 · Swagger: http://localhost:8000/docs
Файл БД SQLite створюється автоматично в `backend/data/app.db`.

### Фронтенд

```bash
cd frontend
npm install
npm run dev
```

Фронтенд: http://localhost:5173 (запити `/api` проксіюються на бекенд).

## Стан розробки

Працюємо поетапно, по одній основній функції.

- [x] Етап 1 — каркас: FastAPI, SQLite-підключення, CORS, єдина схема помилок, `/api/health`; React-каркас із перевіркою бекенда
- [x] Етап 2 — отримання даних із зовнішнього відкритого API (`POST /api/datasets`, JSON/CSV, авто- та ручний `records_path`, SSRF-allowlist, ліміти розміру/рядків), незмінний сирий набір + звірка хешем (`/verify`), перегляд із пагінацією, `DELETE`; UI: форма джерела, список наборів, таблиця сирих даних
- [x] Етап 3 — уніфікація структури: виведення схеми з даних (`GET /api/datasets/{id}/schema`), `POST /api/datasets/{id}/unify` (цільова JSON Schema + маппінг полів або авто), звіт про розбіжності (перейменування, відсутні/зайві поля, колізії, вкладені значення, невідповідність типів), уніфіковані записи з оголошеними типами; UI: панель уніфікації зі звітом і таблицею. Значення поки не перетворюються (це нормалізація), рядки не викидаються (це очищення); результат ще не зберігається — це буде `/process` + `Result`
- [x] Етап 4 — очищення: `POST /api/datasets/{id}/clean` (виконує уніфікацію → очищення). Виявляє пропуски, дублікати, невідповідність типів/форматів, аномалії (IQR); дії на рівні рядків (маркувати / видаляти неповні, видаляти дублікати); реєстр дефектів `{row, field, type, …}` + зведення за типом. Значення не змінюються. UI: панель очищення з опціями, зведенням, реєстром дефектів і таблицею очищених даних
- [x] Етап 5 — нормалізація: `POST /api/datasets/{id}/process` — повний конвеєр уніфікація → очищення → нормалізація (синхронно). Перетворює дати → ISO 8601, числа → канонічний вигляд (роздільники, розрядність), категорії → за явним словником (детерміновано, без fuzzy). Значення без відповідності фіксуються як дефекти. UI: `ProcessPanel` замість окремих панелей — усі три етапи в одній формі, три звіти + таблиця оброблених даних. `/unify` та `/clean` лишаються як утиліти для часткового конвеєра
- [x] Етап 6 — рецепти: модель `Recipe` (версіонована, `recipe_id` + `version`, append-only), `POST/GET/PUT/DELETE /api/recipes`, `GET /api/recipes/{id}/versions`; `POST /process` приймає `recipe_id` (+ `recipe_version`) — тоді беруться правила рецепту. UI: вибір рецепту (підставляє в форму), «зберегти як новий», «зберегти нову версію». Також: дублікати тепер виявляються завжди, прапорець `dedup` керує лише видаленням (позначені дублікати видно у звіті)
- [x] Етап 7 — метрики якості до/після: `POST /process` повертає `metrics` — кількість дефектів (до/після, за типами), повнота ключових полів (до/після), частка збережених записів, час по етапах (уніфікація/очищення/нормалізація/разом). «Після» = повторне виявлення дефектів тим самим детектором на кінцевому наборі. `key_fields` — у рецепті (за замовч. `required` схеми). UI: таблиця до/після з підсвіткою покращень
- [x] Етап 8 — асинхронні задачі: моделі `Job`/`Result`; `POST /api/process {dataset_id, recipe_id?}` → `{job_id}` (фонова `BackgroundTasks`), `GET /api/jobs/{id}` (`pending→processing[stage]→done/error`, timings), `GET /api/jobs?dataset_id=`, `GET /api/result/{job_id}` (метрики + звіти + оброблені дані з пагінацією; `409 job_not_ready` доки не готово). Синхронний `POST /api/datasets/{id}/preview` — прогін без збереження для налаштування. Пайплайн винесено в `services/pipeline.py`. UI: дві кнопки (перегляд / запустити й зберегти), опитування статусу, список збережених обробок
- [x] Етап 9 — візуалізація: окрема сторінка (`#/viz`), вибір набору + версії (сирі дані / будь-яка збережена обробка). Графіки Plotly.js: **стовпчикова, кругова, лінійна**; агрегація (кількість / сума / середнє), фільтр (=, ≠, містить, >, <), масштабування (Plotly). Режим **порівняння до/після** — два графіки поруч. Дані: `GET /api/datasets/{id}/rows`, `GET /api/result/{job_id}/rows`. Plotly вантажиться лениво (окремий чанк)
