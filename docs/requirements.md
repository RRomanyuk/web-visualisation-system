# Вимоги до програмного забезпечення (уточнена редакція)

**Веборієнтована система візуалізації даних з відкритих джерел для наукових досліджень**

> Ця редакція враховує уточнення замовника та закриває прогалини вихідного ТЗ.
> Вимоги можуть коригуватися в ході розробки.

---

## 0. Зміни відносно вихідного ТЗ

| # | Було | Стало |
|---|------|-------|
| 1 | Завантаження файлів CSV/JSON через вебінтерфейс + отримання з REST API | **Лише отримання з відкритих REST API за URL.** Завантаження файлів користувачем не передбачено |
| 2 | «Сесія», механізм зберігання не визначений | **Примітивна вбудована БД (SQLite)**: постійне зберігання сирих наборів, оброблених результатів, рецептів, задач обробки |
| 3 | Цільова схема згадана, але спосіб її передачі відсутній | **Цільова схема — частина рецепту** (JSON Schema). OpenAPI виключено як надлишкове |
| 4 | `/upload`, `/process`, `/result`, `/recipe` без ідентифікаторів | Введено `dataset_id`, `job_id`, `recipe_id`; API перероблено відповідно |
| 5 | Статус обробки без моделі виконання | **Асинхронна обробка**: фонова задача + опитування статусу через `GET /jobs/{id}` |
| 6 | Рецепт: формат і повторне застосування без деталей | Визначено формат рецепту, версіонування, повний CRUD, детермінований маппінг категорій |
| 7 | Межа «очищення / нормалізація» розмита | Розмежовано: очищення **виявляє і фіксує** дефекти та робить дії на рівні рядків; нормалізація **перетворює** значення |
| 8 | Метрики якості описані нечітко | Наведено точні формули для всіх чотирьох метрик |

## 1. Загальний опис

**Призначення.** Веборієнтована система, що інтегрує модуль автоматизованої обробки
відкритих даних (уніфікація, очищення, нормалізація) безпосередньо в процес
інтерактивної візуалізації — без зовнішніх інструментів підготовки даних
(Dataiku, AWS Glue, Talend тощо). Джерело даних — **виключно відкриті REST API**,
доступні за URL.

**Наукова новизна.** Вбудована обробка різнорідних відкритих джерел у межах єдиної
вебсистеми та формування формалізованих показників якості даних, що підвищує
достовірність результатів візуального аналізу в наукових дослідженнях.

**Стек реалізації.**

| Шар | Технологія |
|-----|-----------|
| Серверна частина + модуль обробки | Python 3.11+, **FastAPI**, **pandas** |
| Зберігання | **SQLite** (файл БД, без окремого сервера), доступ через SQLAlchemy |
| Клієнтська частина | **React** |
| Візуалізація | **Plotly.js** (підтримує лінійні/стовпчикові графіки, таблиці, порівняння до/після, фільтрацію, масштабування) |
| Фонові задачі | FastAPI `BackgroundTasks` (для прототипу достатньо; за потреби — черга) |

## 2. Функціональні вимоги

### 2.1 Отримання даних

- Система повинна отримувати дані **із зовнішнього відкритого REST API за
  вказаним URL** (метод GET; за потреби — додаткові query-параметри та заголовки).
- Система повинна підтримувати формати відповіді:
  - **JSON** — масив об'єктів `[ {...}, {...} ]` або об'єкт-обгортка з масивом
    (`{ "data": [...] }`, `{ "results": [...] }` тощо; шлях до масиву задається
    параметром `records_path`, за замовчуванням — автовизначення);
  - **CSV** (`Content-Type: text/csv` або явний `format=csv`) — з налаштовуваним
    роздільником (за замовчуванням `,`) та кодуванням (за замовчуванням `utf-8`,
    резервно `cp1251`).
- Підтримується лише **плоска (таблична) структура**; вкладені об'єкти в JSON
  за замовчуванням не розгортаються (фіксуються як дефект структури на етапі
  уніфікації).
- **Сирі (необроблені) дані зберігаються в БД незмінними** та є доступними
  протягом усього життєвого циклу набору (не лише сеансу) — для порівняння
  до/після обробки. Незмінність контролюється хеш-сумою (`raw_hash`).
- Помилки отримання (недоступний URL, таймаут, некоректний формат, порожня
  відповідь) повертаються як інформативне повідомлення без аварійного завершення.

> **Обмеження безпеки (свідоме).** Запит довільного URL із сервера створює ризик
> SSRF. Для дослідницького прототипу це прийнято; у конфігурації передбачено
> необов'язковий allowlist доменів (`ALLOWED_SOURCE_HOSTS`).

### 2.2 Модуль обробки даних (серверна частина, Python)

Модуль — окремий функціональний компонент між джерелом даних і підсистемою
візуалізації. Виконує три послідовні етапи.

#### Уніфікація структури

- Узгодження назв полів і типів даних відповідно до **цільової схеми (JSON
  Schema)**, що є частиною рецепту (див. 2.3). Якщо рецепт не задано,
  застосовується схема, автоматично виведена із сирих даних.
- Виявлення та фіксація невідповідностей структури вхідних даних очікуваній схемі
  (відсутні поля, зайві поля, перейменування за маппінгом, вкладені структури).
- Результат етапу: набір із приведеними назвами полів та оголошеними типами;
  перелік невідповідностей структури.

#### Очищення

Етап **виявляє та фіксує дефекти** й виконує дії на рівні рядків. Перетворення
значень тут **не виконуються** (це завдання нормалізації).

- Виявлення та обробка **пропущених значень**: маркування або видалення рядків
  (режим задається рецептом, за замовчуванням — маркування).
- Виявлення та видалення **дублікатів записів** (повний збіг рядка або збіг за
  заданим набором ключових полів).
- Виявлення **некоректних типів даних і форматів** (наприклад, дата, записана як
  довільний рядок; число з літерами) та **фіксація їх як дефектів** без зміни
  значення.
- Виявлення **аномалій** у числових полях (за замовчуванням — метод IQR;
  параметри в рецепті).
- Результат етапу: набір після дій на рівні рядків; реєстр дефектів із
  прив'язкою до рядка/поля/типу дефекту.

#### Нормалізація

Етап **перетворює значення** до стандартної форми. Працює із записами, що пройшли
очищення.

- Приведення **форматів дат** до **ISO 8601** (розпізнавання вхідних форматів —
  за списком у рецепті + евристики; нерозпізнані значення позначаються дефектом).
- Стандартизація **числових значень** (десяткові роздільники `,`/`.`, розрядні
  роздільники, одиниці/масштаби за правилами рецепту).
- Нормалізація **категоріальних значень** — зведення варіантів написання до
  одного стандарту за **явним словником відповідностей** (`category_mappings`
  у рецепті) із детермінованою передобробкою (trim, згортання пробілів, нижній
  регістр, опційно — зняття діакритики). Нечіткі підказки можуть пропонуватися
  в інтерфейсі, але **застосовується завжди лише явний словник** → результат
  детермінований.
- Результат етапу: нормалізований набір; перелік значень, які не вдалося
  нормалізувати (дефекти).

### 2.3 Відтворюваність обробки (рецепт)

- Застосовані правила обробки зберігаються в БД як **рецепт** — версіонований
  JSON-документ.
- Структура рецепту:

```json
{
  "id": "rcp_ab12",
  "name": "Обробка бюджетних даних",
  "version": 3,
  "created_at": "2026-09-08T10:00:00Z",
  "target_schema": { "$schema": "…", "type": "object", "properties": { } },
  "field_mapping":   { "Дата операції": "date", "Сума, грн": "amount" },
  "key_fields":      ["date", "amount", "category"],
  "cleaning": {
    "missing_values": "mark",
    "dedup_by": ["date", "amount", "category"],
    "anomaly_method": "iqr",
    "anomaly_params": { "k": 1.5 }
  },
  "normalization": {
    "date_input_formats": ["%d.%m.%Y", "%Y/%m/%d"],
    "decimal_separator": ",",
    "category_mappings": { "київ": "Київ", "м. київ": "Київ", "kyiv": "Київ" }
  }
}
```

- Збережений рецепт **повторно застосовується до нових наборів даних** без
  повторного налаштування (`POST /process` з `recipe_id`).
- Повторний запуск на тих самих вхідних даних із тим самим рецептом дає
  **однакові результати** (детермінізм; жодних випадкових операцій, стабільне
  сортування, фіксований порядок етапів).
- Рецепт має повний CRUD (див. 2.5); редагування створює нову версію.

### 2.4 Оцінка якості даних

Модуль обчислює та повертає такі метрики **до і після обробки**:

| Метрика | Формула |
|---------|---------|
| Кількість виявлених дефектів | `Σ(пропуски + дублікати + некоректні типи/формати + аномалії)` — сума за реєстром дефектів |
| Рівень повноти даних | `непорожні клітинки в ключових полях / (кількість рядків × кількість ключових полів)`; ключові поля — `key_fields` рецепту (за замовчуванням — `required` цільової схеми) |
| Частка збережених записів | `рядків у вихідному наборі / рядків у сирому наборі` (частка записів, що не були відкинуті) |
| Час обробки за етапами | wall-clock у секундах окремо для уніфікації / очищення / нормалізації, а також сумарно |

- Метрики «до» обчислюються на сирих даних за тими самими правилами виявлення,
  що й «після».
- Ці метрики є основою для експериментів 1–4 КР (розділ 2.3 КР). Точні умови
  експериментів беруться з КР; система лише надає значення метрик та порівняльну
  візуалізацію.

### 2.5 REST API

Базовий шлях: `/api`. Формат — JSON. Єдина схема помилки:
`{ "error": { "code": "...", "message": "...", "details": {...} } }`.

| Ендпоінт | Метод | Призначення |
|----------|-------|-------------|
| `/datasets` | POST | Отримати дані з відкритого API за URL, зберегти сирий набір. Тіло: `{ source_url, method?, headers?, query_params?, format?, records_path?, csv_options? }`. Відповідь: `{ dataset_id, row_count, columns, fetched_at }` |
| `/datasets` | GET | Список збережених наборів (метадані) |
| `/datasets/{id}` | GET | Метадані + сирі дані набору (пагінація `?page=&size=`) |
| `/datasets/{id}` | DELETE | Видалити набір і пов'язані результати |
| `/process` | POST | Запустити обробку. Тіло: `{ dataset_id, recipe_id? }` або `{ dataset_id, recipe }` (inline). Створює задачу, повертає `{ job_id, status: "pending" }` |
| `/jobs/{id}` | GET | Статус задачі: `{ status, stage, progress, timings, error? }`, `status ∈ {pending, fetching, processing, done, error}`, `stage ∈ {unification, cleaning, normalization}` |
| `/result/{job_id}` | GET | Оброблені дані + метрики: `{ processed_data, metrics_before, metrics_after, defects, recipe_used }` |
| `/recipes` | GET | Список рецептів |
| `/recipes` | POST | Створити рецепт → `{ recipe_id, version }` |
| `/recipes/{id}` | GET | Отримати рецепт |
| `/recipes/{id}` | PUT | Оновити (створює нову версію) |
| `/recipes/{id}` | DELETE | Видалити рецепт |

- Клієнтська частина відображає **статус обробки** (завантаження → обробка →
  готово) на основі опитування `GET /jobs/{id}`.
- Клієнтська частина відображає **метрики якості до і після** обробки поруч
  із візуалізацією.

### 2.6 Підсистема інтерактивної візуалізації (клієнтська частина)

- Побудова **інтерактивних графіків** (лінійний, стовпчиковий, таблиця) на основі
  оброблених даних (Plotly.js).
- **Порівняльна візуалізація до/після обробки** для підтвердження гіпотези
  дослідження (експеримент 4): графіки метрик якості та розподілів значень
  сирого й обробленого наборів поруч.
- **Фільтрація та масштабування** даних в інтерфейсі.
- Відображення реєстру дефектів (таблиця з фільтром за типом дефекту).

## 3. Нефункціональні вимоги

| Характеристика | Вимога |
|----------------|--------|
| Продуктивність | Обробка набору до **50 000 рядків — не більше 10 секунд** (без урахування часу отримання з зовнішнього API) |
| Надійність | При некоректних вхідних даних або недоступному джерелі — інформативне повідомлення про помилку, без аварійного завершення |
| Незалежність | Система не потребує зовнішніх платформ підготовки даних (Dataiku, AWS Glue, Talend) |
| Відтворюваність | Однакові вхідні дані + той самий рецепт = однаковий результат обробки |
| Зберігання | SQLite; файл БД створюється автоматично при першому запуску; окремий сервер БД не потрібен |
| Розгортання | Локальний запуск: `pip install -r requirements.txt` + `npm install`, без складного налаштування; конфігурація через `.env` |

## 4. Обмеження

- Система є **дослідницьким прототипом**, орієнтованим на перевірку запропонованого
  механізму обробки, а не продакшн-платформою.
- Джерело даних — **лише відкриті REST API за URL**; завантаження файлів
  користувачем не передбачено.
- Підтримуються **табличні дані** у відповідях формату **JSON або CSV** (плоска
  структура).
- **Автентифікація користувачів не передбачена.** БД спільна; конкурентний доступ
  кількох користувачів не є цільовим сценарієм.
- Зберігання — примітивна вбудована БД (SQLite); механізми масштабування,
  реплікації, резервного копіювання поза обсягом роботи.

## 5. Критерії приймання

| № | Критерій | Умова виконання |
|---|----------|-----------------|
| 1 | Отримання даних | URL відкритого REST API успішно приймається; дані завантажуються та зберігаються в БД як незмінний сирий набір |
| 2 | Уніфікація | Модуль виявляє невідповідності структури та узгоджує поля згідно з цільовою схемою рецепту |
| 3 | Очищення | Виявляються пропуски, дублікати, некоректні формати, аномалії; повертається реєстр дефектів та набір після дій на рівні рядків |
| 4 | Нормалізація | Дати, числа, категорії приведені до єдиного формату; нерозпізнані значення позначені дефектами |
| 5 | Метрики якості | Усі чотири метрики до/після обчислюються за визначеними формулами та відображаються коректно |
| 6 | Рецепт обробки | Рецепт зберігається в БД, версіонується та повторно застосовується до нового набору без переналаштування |
| 7 | Відтворюваність | Повторний запуск на тих самих даних із тим самим рецептом дає ідентичний результат |
| 8 | Інтеграція | Клієнт отримує результат обробки через API та відображає його зі статусом обробки |
| 9 | Візуалізація | Порівняльні графіки до/після показують зменшення кількості дефектів і спотворень |

## 6. Відкриті питання (уточнити в ході розробки)

1. Точні умови експериментів 1–4 — узгодити з текстом КР (розділ 2.3).
2. Чи потрібне зберігання історії всіх запусків обробки одного набору, чи лише
   останнього результату.
3. Чи потрібен експорт обробленого набору (наприклад, у CSV/JSON) поза межами API.
4. Перелік конкретних відкритих API, з якими система має бути протестована
   (для формування тестових наборів на 50 000 рядків з реалістичними дефектами).
